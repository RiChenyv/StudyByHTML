00ORIENTATION

先决定学什么，
再开始学 HTTP。

HTTP 的知识量可以无限膨胀。Web 手需要的不是全知，而是对「解析差异」和「信任错位」的敏感度。先建立取舍，后面的每一章才有意义。

这不是一张“协议知识清单”，而是一张攻击面地图。每一条都标了它在 CTF 里通常会变成什么。先看 P0，再决定 P1 什么时候补，P2 现在就可以跳过。

一条判据凡是会影响「谁在什么边界、以什么身份、处理哪段字节」的知识，都是 P0。其余都可以往后放。
60 秒 / 关系

客户端先开口

HTTP 是请求 / 响应协议：浏览器（或 curl / Burp）先发请求，服务器再回响应。没有请求，就没有响应。

60 秒 / 状态

协议本身无状态

每个请求原则上独立。Cookie、Session、JWT 都是在 HTTP 之上“补记忆”，也因此制造了身份攻击面。

60 秒 / 形态

文本或二进制帧

HTTP/1.1 是可读文本 + CRLF；HTTP/2 是二进制帧。底层通常跑在 TCP / TLS 上，HTTP/3 走 QUIC。

P0 / MUST

必须练到肌肉记忆

看到报文就能说出解析顺序与信任边界

+报文骨架与 CRLF
CTF 场景：CRLF 注入、重复头、空行位置错误、body 被当成下一个请求。你要能闭眼写出起始行、头部、空行、body 四段。
+请求边界：Content-Length / Transfer-Encoding
CTF 场景：HTTP 请求走私（CL.TE / TE.CL / H2 降级）。这是 Web 手里“协议层”含金量最高的考点之一。
+URL 解析与百分号编码
CTF 场景：目录穿越、SSRF 绕过、开放重定向、参数污染。重点不是会背编码表，而是知道“哪一层解码了几次”。
+Host 与代理链头部
CTF 场景：Host 头攻击、X-Forwarded-Host 污染、X-Forwarded-For 伪造、缓存投毒。代理和后端信的不是同一套事实。
+Cookie、会话与认证头
CTF 场景：Cookie 属性绕过、会话固定、JWT 算法/声明攻击、Authorization 解析差异。身份通常就藏在这几个头里。
+方法与状态码语义
CTF 场景：方法覆盖绕过 WAF、307 保持方法、401 与 403 的区别、用 405 的 Allow 头摸接口。不要背全表，要背“语义”。
+同源、CORS 与 CSRF
CTF 场景：CORS 错配导致跨域读数据、CSRF 跨站发请求。关键区分：CORS 管“读”，CSRF 管“发”。
+缓存键、Vary 与代理行为
CTF 场景：Web cache poisoning / deception。只要一个输入影响了响应、却没进缓存键，就可能成为毒化入口。
判据 会影响边界、身份、字节解释 → 必须会

为什么跳过：CTF Web 题里出现频率远低于 HTTP/1.1。知道它跑在 QUIC/UDP 上、浏览器会自动协商就够了。

为什么跳过：你只需要知道 HTTPS = HTTP over TLS、SNI/ALPN 影响路由和协议协商。证书链细节不是 Web 手主线。

为什么跳过：你会查。真正要背的是 301/302/307/308、401/403、502/504 这类有语义差的状态码。
+从零写一个高性能 HTTP 服务器
为什么跳过：能读懂解析器行为不等于要自己实现。等你想研究解析器漏洞或造轮子时再学。
+REST 设计美学与 API 规范
为什么跳过：API 设计课有用，但不是 CTF 的入口。你更需要知道资源路由、方法语义和参数位置。
+浏览器渲染与前端框架
为什么跳过：Web 手要懂同源、DOM、CSP 与 JS 执行，但不需要先成为前端工程师。遇到 XSS/DOM 题再补。

每学一个特性，问三句话

① 谁解析它？浏览器、代理、框架还是数据库？
② 谁信任它？这个值有没有被转发、拼接、缓存？

HTTP 走私的本质：
两台机器，

这是 Web 手里最值得反复练的协议章节。你不需要先会打真实靶场，但必须能在纸上指出：前端按哪个头切、后端按哪个头切、剩下的字节去了哪里。

        

        
      

      

        

          

            
尺子 A：Content-Length
“body 有 N 个字节”
CL

            
DECIMAL BYTES
Content-Length: 25

从头读满 25 个 octets，请求结束。

实验是教学简化：真实利用取决于前端/后端的具体实现、连接复用、超时与重试。不要在未授权目标上验证。Burp 默认可能把 chunked 自动解包，测试时务必看原始字节。

        


        

          
CL.TE 一句话前端按 Content-Length 切，后端按 Transfer-Encoding 切。前端把全部字节当一个请求转发；后端在 chunk 0 就结束，剩下的字节被当成下一个请求的开头。

          
TE.CL 一句话前端按 Transfer-Encoding 切，后端按 Content-Length 切。后端只读了很短一截，把 chunk 数据当成下一个请求。

        


        

          
为什么规范写了“TE 优先”，现实还会出问题？
因为规范管不住所有中间件
WHY

          

            

              
RFC 规定同时出现 CL 与 TE 时，接收方应忽略 CL（并且通常应视为错误/关闭连接）。但只要链路上有一个组件不这么干——不支持 TE、在某个条件下忽略 TE、把重复/混淆的 TE 头当成普通头——边界就会分叉。

              
Transfer-Encoding: chunkedTransfer-Encoding : chunkedTransfer-Encoding: xchunkedduplicate headersspace / tab tricks

            

            
TE.TE前后端都支持 TE，但其中一个被“混淆的 TE 头”骗到不处理。攻击者用大小写、空格、重复头、编码差异制造“一个认、一个不认”。

          

        


        

          
防守方拒绝同时带 CL/TE 的请求；统一规范化；前后端使用同一套严格解析；尽量 HTTP/2 端到端，避免降级；不要盲目复用后端连接。

          
CTF 手先判断“谁用 CL、谁用 TE”，再构造能同时满足两边的边界；观察时序、响应错位、下一个请求被影响。看到 502/504 或响应串线，不要忽略。

只解码，不验证。 JWT 的 payload 是明文（Base64URL，不是加密）；签名只证明“未被篡改”，前提是服务器正确校验。

              

              

            

            

              
alg:none
如果服务器接受空签名/none，攻击者可直接改 payload。

              
算法混淆
HS256 与 RS256 用错公钥/私钥时，可能把公钥当 HMAC 密钥。

              
声明未校验
role、exp、aud、iss、kid、jku 只要有一个没校验，就可能出问题。

            

          

        


        
身份三问谁签发？Cookie/Session 由服务端签发，JWT 由持有密钥的一方签发。谁携带？浏览器自动带 Cookie，Authorization 要客户端显式加。谁验证？真正的权限判断必须在服务端，且要与资源绑定。

      

    


    

    

      

        

          
08SAME-ORIGIN & CORS

          
浏览器允许请求，
不等于允许你读响应。

          
CORS 经常被误解成“服务器端的访问控制”。它其实是浏览器的一套读取许可：请求可能已经发出、已经产生副作用，但 JS 仍然看不到响应。

一句话记住 CORS服务器说“谁能读”，浏览器负责执行。请求是否发出与响应是否可读是两条独立的路；CORS 错配可能让攻击者读走数据，但不会阻止 CSRF 把请求发出去。

09CACHE & PROXY

          
缓存只认键，
不认你的意图。

          
缓存投毒的核心问题只有一个：某个输入改变了响应，却没有进入缓存键。攻击者把自己的响应存进去，下一个受害者取走它。

② SHARED CACHE

关键：缓存键通常包含 scheme、host、path、query，以及 Vary 指定的头。任何能影响响应内容的头（XFH、XFF、User-Agent、Accept-Language…）如果没进键，就可能是 unkeyed input。

“网站叫什么”也是用户输入

X-Forwarded-For 信任链

10HTTP/2 & DOWNGRADE

          
二进制分帧让边界更稳，
但降级会把旧问题带回来。

          
HTTP/2 不是“更快的 HTTP/1.1 文本”，而是另一套帧协议。你不需要手写 HPACK，但要知道伪首部、流、以及 H2 → H1 降级为什么仍是 CTF 考点。

        

        
      

      

        

          
帧时间线
点击任意帧，查看它在这一跳里做什么
FRAMES

          

          

          
提示：真实 HTTP/2 帧是二进制，头部还可能经过 HPACK 压缩；这里展示的是解码后的语义，用来理解结构。

        


        

          

            
同一请求，两种表达
HTTP/2 用伪首部；HTTP/1.1 用起始行 + Host
COMPARE

            

              
HTTP/2 / HEADERS
:method: GET
:path: /admin
:scheme: https
:authority: ctf.local
cookie: session=…


              
HTTP/1.1 / RAW
GET /admin HTTP/1.1
Host: ctf.local
Cookie: session=…


            

            
H2 头名必须小写；Connection、Transfer-Encoding 等逐跳头被禁止（TE: trailers 例外）。边界由帧长度保证。

          

          

            
降级：H2 进来，H1 出去
现代架构最常见的安全缝隙
DOWNGRADE

            
FRONT-END → BACK-END
客户端：HTTP/2 + 帧长度
        ↓ 翻译 / 降级
后端：HTTP/1.1 + CL 或 TE

content-length: 0  ← 被注入的头？
transfer-encoding: chunked


            
如果前端用 H2 的帧长度，后端却相信降级后生成的 CL/TE，就可能重现 H2.CL / H2.TE 走私；CRLF 注入进头值也是 H2 特有的危险。

          

        


        

          
流 / Stream一条连接上并发多条流，每帧带 stream ID。响应可以交错回来，靠流 ID 归位。

          
伪首部:method / :path / :scheme / :authority 是请求元数据；重复、缺失或与 Host 冲突都可能被利用。

          
HTTP/3跑在 QUIC/UDP 上，帧与流模型继续演进。知道它存在即可；CTF 里先把 H1/H2 的解析差异吃透。

        

      

    


    

    

      

        

          
11FIELD WORKFLOW

          
从“看报文”到
“拿到可复现的证据”。

          
CTF 里最浪费时间的不是不会 payload，而是没有基线、没有控制变量、没有可复现命令。把下面这套流程练成习惯，比多背十个头更有用。

        

        
      

      

        

          

            
六步工作流
从入口到证据
LOOP

            

              
01
抓一个真实请求
浏览器 + 代理，先看清 Host、Cookie、Content-Type、body 与响应头。不要凭页面猜。

              
02
记录基线
状态码、关键头、body 长度、耗时。后面所有差异都相对它。

              
03
只改一个变量
路径 / Host / CL / Cookie / Origin 一次只动一个。否则你不知道哪个变化导致了结果。

              
04
对比差异
401→200、403→200、302 目标变化、响应长度变化、时序变化、缓存命中，都是信号。

              
05
用 curl 原样复现
把 Burp 里的请求变成可重复的命令，排除浏览器自动头与工具自动修正。

              
06
写清楚结论与边界
“为什么能”“影响是什么”“怎么修”。别只留一个 payload。
