00 / FIRST THINGS FIRST起步

HTTP 是什么？

学完能说清：谁在和谁说话，说的是什么。

HTTP 是浏览器与服务器交换资源的一套约定。全称是 Hypertext Transfer Protocol，中文叫“超文本传输协议”。“协议”可以理解为双方都遵守的沟通规则：怎样提要求，怎样回复，怎样说明成功或失败。

把访问网站想成去图书馆借书：你告诉管理员“我要哪一本”，管理员回答“找到了，这是书”或“没有这本书”。在网站里，你的浏览器提出请求（request），服务器返回响应（response）。HTTP 规定了这两种消息的格式和含义。

客户端
发起请求的软件。常见的是浏览器，也可以是手机 App 或命令行工具 curl。
服务器
接收请求、处理请求并提供内容的软件，也常指运行这些软件的计算机。它可以在远处，也可以在你自己的电脑上。
资源
你想获取或操作的东西：网页、图片、视频、文件，或一份用户资料。
网页与网站
网页是你看到的一页内容；网站通常是一组相关网页与服务。一个网页往往需要多份资源才能显示完整。
前端与后端
前端主要负责浏览器中的界面与交互；后端在服务器上处理数据与业务。两者经常用 HTTP 交换信息。
接口 / API
软件之间约定好的访问入口。例如 /api/books 返回书籍数据，供网页或 App 使用，不一定返回可直接阅读的网页。

一个网页，并不只对应一次请求

浏览器可能先取得 HTML（描述网页结构的文档），读到里面的引用后，再请求 CSS（控制样式）、JavaScript（实现交互）和图片。页面滚动或点击按钮时，还可能继续请求数据。所以，看到一个网页通常意味着背后发生了多次 HTTP 对话。

先记住三个事实

① 普通 HTTP 交互由客户端先发请求。② 响应可以是图片或数据，不只是网页。③ HTTP 本身不替网站自动记住“你是谁”；登录状态由后面的 Cookie、会话等机制实现。

“无状态”说的是：每次请求都需要提供足够的信息，服务器才能理解它。它不表示网站不能存数据，也不表示每次请求都必须重新建立网络连接。“有没有登录”和“连接有没有复用”是两个不同问题。

停下来想一下：在地址栏输入网址，谁是客户端？

浏览器是客户端；提供网站内容的一方是服务器。它们先交换请求和响应，浏览器再把收到的内容组织成你看到的页面。

本章一句话：HTTP 帮助客户端“提出请求”，帮助服务器“给出回答”。

01 / THE JOURNEY起步

打开网页时，发生了什么？

理解 HTTP 所处的位置，分清“找地址”“建连接”和“传内容”。

假设你在浏览器里输入 https://example.com/books，按下回车。这里先看一次没有可用连接、需要访问网络的典型过程；浏览器实际可能复用连接或直接使用缓存，跳过某些步骤。

  1. 读懂网址：你想去哪？

    浏览器识别协议、网站名称和资源路径。比如你想通过 HTTPS 访问 example.com 的 /books。

  2. 查找地址：DNS 把域名对应到 IP

    域名是便于人记忆的名称，IP 地址用于网络定位。DNS 像通讯录，帮你查询名称对应的地址；结果可能已在缓存中。

  3. 建立通道：连接与加密

    HTTP/1.1 和 HTTP/2 通常使用 TCP，提供可靠、有序的数据传输。HTTPS 还使用 TLS，验证服务器身份并保护传输中的数据。HTTP/3 使用 QUIC，见第 11 章。

  4. 发送请求：我要 /books

    请求说明想做什么、访问什么资源，并携带服务器需要的其他信息。

  5. 服务器处理并回应

    可能查数据库、判断是否登录，最后返回状态码、头部和正文。途中也可能经过代理或缓存。

  6. 浏览器显示页面并继续加载

    浏览器处理响应，如果内容是 HTML，就解析网页并继续请求其中引用的图片、样式等资源。

TRY 01 / 在页面内模拟

逐步看一次访问

点击步骤，区分每一层解决的问题。

HTTPS 多了什么？

HTTPS 可以先理解为“受到 TLS 保护的 HTTP”。HTTP 说明双方交换的消息是什么意思；TLS 负责保护传输，让旁观者难以窃听、篡改，并通过证书等机制验证服务器身份。浏览器与 TLS 终止点仍然能够读取内容；TLS 终止点可能是网站前面的代理。

HTTPS 不意味着网站上的所有内容都可信，也不替代登录与权限检查。不要把密码放在 URL 里：即使传输已加密，URL 仍可能进入历史记录、日志或被复制分享。

概念可以先理解成解决的问题
域名 / DNS名称 / 通讯录网站的网络地址是什么？
IP + 端口楼的地址 + 服务窗口连接哪台主机的哪项服务？HTTP 默认端口 80，HTTPS 默认 443。
TCP / QUIC传输通道数据怎样可靠地送达？
TLS身份核验 + 通道保护与谁连接？途中如何防窃听和篡改？
HTTP对话规则要什么资源？返回什么结果？

本章一句话：先找到服务器、建立合适的通道，再通过 HTTP 交换内容。

02 / ADDRESS起步

网址里，每一段是什么意思？

把 URL 拆成六部分，知道哪些内容会发送给服务器。

URL（统一资源定位符）是资源的地址。先看这个例子：

https://example.com:443/books?q=http&page=2#reviews
└协议┘ └──主机名──┘ 端口 └路径┘ └─查询参数──┘ └片段┘
部分示例它在说什么？
协议 / schemehttps使用哪种访问方式。
主机 / hostexample.com访问哪一个网站；也可能直接是 IP 地址。
端口 / port443访问主机的哪个服务入口。默认端口通常省略。
路径 / path/books站点里的哪个资源。它是逻辑地址，不一定对应磁盘文件夹。
查询 / queryq=http&page=2常用来传搜索词、页码等参数。? 开始，常用 & 分隔、= 连接名称和值；具体意义由应用决定。
片段 / fragmentreviews# 后的内容，用于页面定位或前端路由，不会作为 URL 的片段随 HTTP 请求发送。
TRY 02 / URL 拆解

换一个网址，看看结构怎么变

只在本地解析，不会访问输入的网站。

相对地址与编码

/books 是相对当前站点根目录的地址。若页面位于 https://example.com/guide/start，链接 next 通常会被解析为 https://example.com/guide/next。浏览器需要结合当前页面地址（或指定的基准地址）补全它。

URL 中有些字符有特殊含义。比如参数值本身包含 & 时，常编码成 %26，以免被当作参数分隔符。中文通常先变成 UTF-8 字节，再逐字节写成 % 加两位十六进制。百分号编码是表示方式，不是加密。

容易混淆：在表单 URL 编码中，+ 常表示空格；在 URL 的其他位置，不能一概这样解释。重复参数 ?id=1&id=2 最终取第一个、最后一个还是数组，取决于应用如何解析。
停下来想一下：/books?page=2#reviews 中，服务器会看到 #reviews 吗？

不会。常见的 HTTP/1.1 请求目标是 /books?page=2。片段由浏览器处理；页面脚本仍可能读取片段并另外发起请求，那属于后续行为。

本章一句话：URL 告诉浏览器“通过什么方式，去哪里，取什么资源”。

03 / MESSAGES基础

拆开一条请求，再读一条响应

认出起始行、头部、空行和正文，不再把它们混在一起。

HTTP 消息也叫报文。为了看清结构，下面使用容易阅读的 HTTP/1.1 文本格式。HTTP/2 和 HTTP/3 的线上格式不同，但方法、状态码、头部等基本含义仍适用。

请求：客户端提出要求

GET /hello HTTP/1.1
Host: example.com
Accept: text/plain

GET：想读取资源。/hello：资源路径。Host：要访问的网站。这里没有请求正文，头部后的空行仍然重要。

响应：服务器给出回答

HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
Content-Length: 5

Hello

200：这次请求成功。Content-Type：正文是 UTF-8 文本。Content-Length: 5：正文的长度是 5 字节。

按四个部分来读：

① 起始行：请求写“动作 + 目标 + 版本”，响应写“版本 + 状态码”。② 头部（header）：补充说明，一行一个字段。③ 空行：头部到这里结束。④ 正文（body）：实际数据，可以没有。

TRY 03 / 逐行阅读

点一行，看它的作用

示例发送表单正文 name=Li，共 7 个 ASCII / UTF-8 字节。

点击“空行”也有解释。显示时使用普通换行；HTTP/1.1 标准行结束符是 CRLF（\r\n，即回车加换行）。

头部和正文的区别

把它们想成快递包装：头部像包裹标签，正文像包裹里的东西。标签可以说明“里面是 JSON、长多少字节、能不能缓存”；正文才是实际的文字、图片或数据。同名字段可以出现在不同方向，例如请求与响应都能携带 Content-Type，分别描述各自的正文。

一台服务器可能同时提供多个网站。HTTP/1.1 的 Host 告诉它你要找哪一个。头部名称不区分大小写，Content-Type 与 content-type 是同一个字段；方法名称则区分大小写，通常写成 GET、POST。

本章一句话：先读起始行，再读头部，越过空行后才是正文。

04 / INTENT & RESULT基础

方法表达意图，状态码说明结果

先掌握常见语义，再遇到具体代码时查阅。

方法：你想对资源做什么？

同一个地址，可以使用不同方法。例如 GET /books 获取书单，POST /books 提交新书。具体允许哪些操作，由服务器的接口约定决定。

方法通常的意图例子安全 / 幂等
GET读取资源查看书单是 / 是
HEAD取得类似 GET 的元信息，响应不含正文了解资源类型、大小是 / 是
POST让资源处理所提交的数据提交订单、发送表单否 / 不保证
PUT创建或完整替换目标资源的状态整体替换一份资料否 / 是
PATCH对资源应用部分修改只改资料中的昵称否 / 不保证
DELETE请求删除目标资源删除一条记录否 / 是
OPTIONS询问通信选项CORS 预检常用是 / 是

安全（safe）指客户端没有请求改变服务器上的业务状态，例如读取书单；服务器照常写访问日志不违背这一点。幂等（idempotent）指同一个请求执行一次或重复执行，对服务器的预期影响相同，不要求响应完全相同。例如第一次删除返回 204，第二次返回 404，仍可以符合 DELETE 的幂等语义。

这里的“安全方法”是协议语义，不代表连接已经加密。GET 和 POST 都可经 HTTPS 传输；POST 本身不会加密数据。不要用 GET 执行转账、删数据等操作。

状态码：这次请求的结果如何？

家族大意先记这些
1xx过程信息100 Continue：可以继续发请求内容。
2xx成功处理200 成功；201 已创建；204 成功但无响应正文；206 部分内容。
3xx进一步动作或使用缓存301 / 302 等用于跳转；304 表示缓存版本仍有效，不是跳到另一个网页。
4xx请求方面的问题400 请求有误；401 缺少有效认证；403 拒绝执行；404 未找到；405 方法不允许；429 请求过多。
5xx服务器处理方面的问题500 内部错误；502 网关收到无效上游响应；503 暂不可用；504 网关等待上游超时。
TRY 04 / 情景判断

如果你是服务器，会怎么回复？

401 与 403 不只是“没登录 / 已登录”的二分。401 表示请求缺少有效的认证凭据，并应带 WWW-Authenticate 说明认证要求；403 表示服务器理解请求但拒绝执行，原因可能是权限或其他规则，也不保证用户已经登录。服务器有时会用 404 隐藏资源是否存在。

补充：重定向会不会把 POST 变成 GET？

响应的 Location 指明跳转目标。客户端是否跟随由自身策略决定；浏览器通常会跟随。

代码含义方法处理
301 / 302永久 / 临时跳转历史兼容行为允许 POST 改成 GET；不要依赖它保持提交内容。
303去另一个位置取结果通常用 GET 取结果；HEAD 可保持 HEAD。常用于提交表单后跳到结果页。
307 / 308临时 / 永久跳转自动跟随时必须保持方法和请求正文。

本章一句话：GET / POST 等说明“想做什么”，200 / 404 等说明“结果怎样”。

05 / HEADERS基础

头部：消息自带的说明书

先认识最常见的八个字段，其余按需查找。

头部（也叫“首部”）通常写成 名称: 值。不必一口气记住所有字段，先问它是在说明目标、数据、身份，还是处理规则。

字段方向用一句人话理解
Host请求我要访问这个网站。HTTP/1.1 必须携带。
Accept请求我希望接收这些类型的内容，如 JSON。
Content-Type双方这条消息的正文是什么类型，如图片、JSON 或表单。
Content-Length双方消息内容的字节长度；使用时必须符合该类消息的规则。
Cookie请求浏览器把符合条件的已存 Cookie 带给服务器。
Set-Cookie响应服务器让浏览器保存或更新一条 Cookie。
Cache-Control双方说明与缓存有关的要求和策略。
Location响应跳转目标，或刚创建资源的位置。
Accept 与 Content-Type：

Accept: application/json 是“我希望收到 JSON”；Content-Type: application/json 是“我正在发送的正文就是 JSON”。服务器不一定能满足所有偏好，最终应看响应的 Content-Type。

LOOK UP / 按需查询

常见头部索引

输入名称或中文用途，再展开查看。无需全部背诵。

补充：重复头部与逐跳头部

不要把所有重复字段都简单地用逗号连接。Set-Cookie 可以出现多次，分别设置 Cookie；错误合并会改变意义。Content-Length 等影响消息边界的字段需要严格验证。

大部分头部描述端到端的消息，有些只对当前相邻连接有效，称为“逐跳”。HTTP/1.1 的 Connection 就属于此类，代理转发时需要正确处理。HTTP/2 不允许 Connection 这类连接专用字段。

本章一句话：正文是内容，头部告诉接收方应该怎样理解和处理这些内容。

06 / DATA基础

正文装什么？长度又怎样计算？

分清数据格式、字符编码、压缩与加密。

请求正文常用来提交数据，响应正文则承载返回的内容。正文不只是文本，也可以是文件的二进制数据。发送方需要正确说明格式，接收方才能用相应的方式解析。

Content-Type示例或用途怎样理解
text/plain; charset=utf-8你好普通文本，按 UTF-8 解释文字。
text/html; charset=utf-8<h1>你好</h1>网页结构。浏览器按 HTML 处理。
application/json{"name":"Li","age":20}结构化数据；字符串和属性名用双引号，数字不加引号。
application/x-www-form-urlencodedname=Li&city=Beijing表单键值对，参数按表单规则编码。
multipart/form-data; boundary=…上传头像，同时提交昵称用边界分隔多个部分，可同时装普通字段和文件。浏览器提交 FormData 时应让它自动生成 boundary。
image/png / application/pdf图片 / PDF 文件正文是对应文件内容，不应当作普通文字读。

字符不是字节

字符是我们看到的文字单位；字节（byte）是计算机存储和传输数据的单位，一个字节有 8 个二进制位。在 UTF-8 中，英文字母 A 占 1 字节，汉字 你 占 3 字节，许多单个 emoji 占 4 字节。

Content-Length 关注字节长度，不是屏幕上有几个字。正文是 你好 时，UTF-8 编码长度是 6 字节。如果正文又被 gzip 等方式压缩，Content-Length 在适用时描述的是压缩后发送的内容长度，不是解压后文字的长度。

07 / IDENTITY应用

HTTP 无状态，网站怎样记住我？

用一次登录理解 Cookie、Session 和 Token 的分工。

浏览器先请求首页，再请求“我的资料”。后一个请求怎样表明“还是刚才那个用户”？一种常见做法是：服务器保存一份会话记录，浏览器保存对应的会话编号，之后把编号带回来。

  1. 提交登录信息

    浏览器经 HTTPS 提交账号和密码，服务器检查是否正确。

  2. 建立会话，并让浏览器记住编号

    服务器创建 Session（会话），把用户与随机会话 ID 关联；响应携带 Set-Cookie: session=随机编号; …。

  3. 之后的匹配请求带上 Cookie

    浏览器按域名、路径、安全和站点等条件决定是否附带 Cookie: session=随机编号。

  4. 服务器识别并检查权限

    服务器查出会话对应的用户，再判断他是否有权访问该资源。退出登录时要让服务器端的会话也失效。

Cookie 是浏览器保存的数据

Cookie 通常是小段键值对，可用于会话编号、偏好设置等。它不是登录机制的同义词，也不一定装着账号和密码。匹配条件下，浏览器通常会自动携带它。

Session 是一种会话机制

常见的 Session 数据保存在服务器一侧，浏览器只持有不透明的编号。登录成功后通常应更换会话 ID，避免会话固定问题。

属性主要作用不能误解为
Secure要求通过安全连接发送，通常是 HTTPS（本机等有特殊规则）。不代表 Cookie 值已经单独加密。
HttpOnly不允许页面脚本通过 document.cookie 读取。不会阻止浏览器发送 Cookie，也不能单独防住 CSRF 或所有 XSS 影响。

Token 和 JWT 又是什么？
Token 可以理解为客户端携带的令牌。某些接口使用 Authorization: Bearer 令牌，一般由客户端程序显式添加。身份认证回答“你是谁”，授权回答“你能做什么”；两项都应该由服务端检查。
JWT 是一种令牌格式。常见的签名 JWT 由三段组成：头部、载荷、签名，前两段通常用 Base64URL 表示。能解码不等于能伪造；签名也不等于加密。服务端必须验证签名、允许的算法以及有效期、签发方、接收方等适用声明，不能相信客户端自己填的 role=admin。

08 / REUSE & INTERMEDIARIES应用
为什么第二次访问常常更快？
分清直接用缓存、向服务器校验，以及 304 的作用。


缓存是把已经获得的响应保存起来，在规则允许时复用。浏览器可以保存自己的私有缓存；CDN 或代理可以提供多用户共用的共享缓存。合理复用能减少等待和网络传输，但个性化信息不能随便共享。


两种常见的复用方式
  1. 还在新鲜期：直接使用。例如响应写了 Cache-Control: max-age=60，在满足其他条件的情况下，60 秒的新鲜期内可复用，不必每次问服务器。
  2. 需要验证：先确认版本。响应带 ETag: "book-v1"，之后客户端发送 If-None-Match: "book-v1"。对 GET / HEAD，如果版本未变，服务器可以返回 304 Not Modified，让客户端继续使用已存内容；变了则通常返回 200 和新内容。


指令实际意思
max-age=60指定响应的新鲜时间为 60 秒。缓存年龄的计算也会考虑 Date、Age 等信息。
no-cache可以存储，但复用前必须成功验证。名字容易误导。
no-store要求缓存不要存储这次消息；不保证清除此前所有副本。
private只能由私有缓存存储，共享缓存不能存储。
s-maxage=60对共享缓存指定新鲜时间，覆盖该处的 max-age。
Vary: Accept-Language复用时还要匹配 Accept-Language，不应把中文响应当成英文版本复用。


TRY 07 / 缓存决策
这次需要访问服务器吗？
简化模型：已有一次 GET 的 200 响应、同一私有缓存、无其他限制；版本验证使用 ETag。


代理站在对话中间
正向代理代表客户端对外访问；反向代理代表网站接收请求，再转交后端。CDN（内容分发网络）常在靠近用户的节点提供缓存等服务；WAF（Web 应用防火墙）按规则检查或拦截请求。一条请求可能经过多层中间节点。
浏览器 → CDN / 反向代理 → 应用服务器 → 数据库
       ← 缓存或后端生成的 HTTP 响应 ←


缓存靠缓存键区分内容，通常涉及方法、目标 URL 及 Vary 指定的字段，细节由实现和配置决定。如果用户的身份会改变响应，缓存策略却把私人内容错误共享，就可能串用数据。X-Forwarded-For 等代理头也不能无条件当成真实身份来源，必须结合可信代理配置。


本章一句话：缓存可以直接复用，也可以先验证；304 让客户端继续使用已有正文。







09 / BROWSER RULES应用
请求成功了，为什么脚本却读不到？
分清同源、CORS 和 CSRF，避免把“能发出”当作“能读取”。


浏览器会执行同源策略，限制一个来源的脚本随意读取另一个来源的敏感内容。这里的“源”（origin）由协议、主机、端口共同确定，三者都相同才算同源；路径不同不影响同源。


与 https://example.com/books 比较是否同源原因
https://example.com/profile是只改了路径。
http://example.com/books否协议不同。
https://api.example.com/books否主机不同，子域也算不同主机。
https://example.com:8443/books否端口不同；省略端口的 HTTPS 默认是 443。


CORS：服务器声明可以让谁读
例如页面在 https://app.example.com，脚本用 fetch 读取 https://api.example.com。API 可以在响应中返回 Access-Control-Allow-Origin: https://app.example.com，浏览器据此决定是否把响应交给脚本。这套机制叫 CORS（跨源资源共享）。
有些跨源请求可以直接发出；某些方法或头部会触发 OPTIONS 预检，浏览器先询问服务器是否允许，成功后才发送实际请求。例如跨源 JSON POST 通常会触发预检。预检失败时，实际请求不会发出；直接发送的请求则可能已被服务器处理，只是响应不允许脚本读取。


TRY 08 / CORS 决策
浏览器会允许读取这份响应吗？
教学模型：app.example.com 跨源 fetch 到 api.example.com；服务器均成功响应预检/实际请求。Cookie 是否真的携带仍受匹配规则和浏览器策略约束。


带凭据的跨源读取：
使用 credentials: "include" 时，Allow-Origin 必须是具体的允许来源，不能是 *，还需要 Access-Control-Allow-Credentials: true。即使当前没有 Cookie，这个 credentials 模式仍受该规则约束。CORS 不是服务端的身份认证，非浏览器客户端通常不执行它。


CSRF：借用浏览器自动携带的身份发请求
CSRF（跨站请求伪造）是诱导已登录用户的浏览器发出非本人意愿的操作。例如访问恶意页面时，它尝试向购物网站提交更改邮箱的表单；如果浏览器带了登录 Cookie、服务端又缺少校验，就可能执行成功。攻击者未必需要读到响应。
常见防护包括服务端校验 CSRF Token、检查 Origin 等来源信息、合理设置 SameSite，并避免让 GET 执行修改操作。CORS 可以限制跨源读取，但不能单独解决所有 CSRF 风险。
同站不等于同源。现代浏览器的 SameSite 判断通常考虑协议和可注册域：https://app.example.com 与 https://api.example.com 通常同站，但不同源。同站判断还涉及公共后缀规则，不能简单截取域名的最后两段；Cookie 的 Domain 匹配又是另一个问题。


本章一句话：先问请求是否发出，再问响应能否读取；这两件事可能有不同答案。

11 / VERSIONS拓展
版本变了，对话的基本含义没变
理解文本、帧与流的区别，不把开发者工具的显示当作原始线上字节。


前面为了便于学习，使用了 HTTP/1.1 文本报文。真实网页也可能使用 HTTP/2 或 HTTP/3。它们仍然有请求方法、响应状态、头部和正文，主要改变了这些信息怎样组织和传输。


版本传输与组织先理解这个特点
HTTP/1.1通常基于 TCP，起始行和头部为文本；正文可为二进制。连接可复用；消息结束位置需要严格规则。浏览器常用多个连接提高并行度。
HTTP/2通常在 TLS + TCP 上使用二进制帧和多个流；头部采用 HPACK 压缩。同一连接可以并发交换多个请求/响应，帧用流 ID 区分；TCP 丢包仍可能拖慢其他流。
HTTP/3使用 QUIC（基于 UDP，集成 TLS 1.3），头部采用 QPACK。不同流有独立的可靠传输，缓解跨流的传输层队头阻塞；不等于丢包对性能毫无影响。


HTTP/2 的伪首部
HTTP/2 不使用 GET /books HTTP/1.1 这样的文本请求行，而是使用以冒号开头的伪首部表达部分元信息。下面只是解码后便于人阅读的展示，实际线上数据是二进制帧。
:method: GET
:scheme: https
:authority: example.com
:path: /books
:status: 200
content-type: application/json

（正文在 DATA 帧中传输）


HTTP/2 的字段名必须小写；不能发送 Connection、Transfer-Encoding 这类连接专用字段，TE 只有 trailers 这一允许值。即使带了 Content-Length，也必须与对应 DATA 内容长度匹配，否则属于畸形消息。


补充：WebSocket 和流式响应
WebSocket 用于持续的双向通信。在经典 HTTP/1.1 握手中，服务器可用 101 Switching Protocols 接受 Upgrade，随后使用 WebSocket 的消息格式；HTTP/2、HTTP/3 有不同的接入机制。
HTTP 的响应正文也可以逐步发送，例如下载大文件，或通过 SSE（Server-Sent Events，服务器发送事件）持续接收服务器事件。这不要求把普通 HTTP 理解成“每次只能发一小段文字”。


本章一句话：各版本保留核心语义，用不同方式让消息在网络上传输。







12 / MESSAGE BOUNDARIES进阶 · 可第二遍读
一条消息在哪里结束？
理解消息边界，再理解原稿中的请求走私概念。


一条连接可能先后传多条消息。接收方必须知道：哪些字节属于当前正文，后面的字节从哪里开始属于下一条消息。HTTP/1.1 不是靠“多留一个空行”判断正文结束。空行只分隔头部和正文，正文长度还需要另外的规则。


Content-Length 与 chunked
Content-Length: 5 表示按规定读取 5 个正文内容字节。另一种机制是 Transfer-Encoding: chunked，把内容分块，每块前写十六进制大小，最后用零块结束，还可以包含尾部字段（trailer）。例如：
Transfer-Encoding: chunked

5\r\n
Hello\r\n
0\r\n
\r\n
这里把 CRLF 显示成可见的 \r\n 以便数清。解块后的内容只有 Hello。上方大小 5 指数据块的 5 字节，不包括分块语法本身。


并非所有响应都靠 Content-Length 结束：HEAD 的响应，以及 1xx、204、304 等，按规则没有消息正文；某些 HTTP/1.1 响应也可以通过关闭连接确定结束。304 / HEAD 中 Content-Length 另有元信息含义，不能见到它就认定后面一定有同样长度的正文。


TRY 10 / 边界差异模型
两台解析器，会读到同一个结束位置吗？
仅展示概念，不发送请求。下面的 A、B 为无害标记，不是可执行走私报文。


请求走私：前后端对边界的理解不同
请求经过前置代理与后端时，若两者切分消息的规则不同，同一段字节在一端属于“正文”，在另一端却可能成为“下一个请求”的开头。这类不同步问题称为请求走私。CL.TE 按“前端、后端”顺序命名；TE.CL 则相反。TE.TE 常指双方对不同写法的 Transfer-Encoding 处理不一致，最终形成类似歧义。


规范和有缺陷的实现要分开：
发送方不能同时发送 Content-Length 与 Transfer-Encoding。接收方遇到两者时 TE 的边界规则优先，但应把它视为可能的走私风险并按严格规则处理；若中间节点选择转发，必须先移除 Content-Length。接收这种请求的服务器在响应后必须关闭连接。不能把实验中的错误解析行为当成合法格式。详见 RFC 9112 §6.3。


HTTP/2 使用帧和流约束消息边界，没有经典 H1 的 CL/TE 切分方式。但如果前端接收 H2、转给后端时降为 H1，且转换时长度或字段校验有误，就可能产生 H2.CL、H2.TE 等问题。不能因此认定“用了 H2 就完全没有解析风险”。


防护重点是严格解析、拒绝歧义、正确转换协议并及时更新代理和后端；保持前后端一致的规则。在 CTF 或明确授权的测试环境中，观察现象也需要考虑连接复用、超时和工具是否自动修改长度。


本章一句话：前后端必须同意一条消息在哪里结束，否则字节就可能被错认。







13 / SECURITY PERSPECTIVE进阶 · 按需查阅
把 HTTP 知识连接到 Web 安全
知道该观察哪一层，而不是把每个头部都当成漏洞。


原稿侧重 CTF Web，本章保留这条进阶路线。CTF 是通过靶场题目学习安全技术的一种竞赛形式；Burp 等调试代理可帮助观察、编辑和重放授权环境中的请求。漏洞通常来自不正确的信任、解析或业务校验，而不是某个字段“存在就危险”。


01 · URL、路径与解析差异
浏览器、反向代理、框架可能分别规范化 URL、解码百分号、处理重复参数。若鉴权组件检查的路径与路由实际使用的路径不同，就可能放行不该访问的资源。
SSRF 是服务器端请求伪造：应用按用户输入去请求另一个地址，却缺少恰当限制；应检查允许的协议、目标地址、DNS 结果与重定向的后续目标。开放重定向 则是不当信任跳转目标。二者都需要明确“谁在解析、谁在访问”。


02 · Host、代理头与缓存投毒
Host、X-Forwarded-Host 可能被应用用于生成绝对链接；X-Forwarded-For 常记录代理链看到的地址。如果后端无条件相信客户端自己发送的代理头，就可能把伪造信息用于访问控制或链接生成。
缓存投毒 的一种条件是：某个可控输入影响了可缓存响应，却没有被正确纳入缓存区分规则，攻击者的响应便可能被其他用户取到。正确的信任边界、缓存键、Vary 和敏感内容策略缺一不可。缓存欺骗则涉及把私人响应错误当成可共享的静态资源缓存。
防护需要可信代理清洗与设置转发字段、配置后端信任范围、验证允许的 Host，并对响应的共享与变化因素作明确约束。


03 · 身份、对象权限与 JWT
仅仅能“登录”不代表能访问所有用户的数据。例如 /api/orders/123 必须校验当前用户对订单 123 的权限；不能只看参数里写了谁。缺少这种校验的情况常称为 IDOR（不安全的直接对象引用）。
会话应具备足够随机性，登录后轮换会话编号，退出后失效。JWT 应限制算法并验证签名与适用声明，不接受不期望的无签名令牌；从不可信位置取得验证密钥也会带来风险。Base64 解码成功不能证明可信。


04 · 正文解析、注入与上传
SQL 注入 是不可信输入被当成数据库指令的一部分；XSS 是不可信内容在浏览器上下文中变成脚本等可执行内容。它们需要结合应用代码和上下文分析，不能仅凭 HTTP 状态码判定。
Content-Type 会影响后端使用表单、JSON、XML 等哪种解析器。文件上传还涉及 multipart 边界、文件名、真实文件类型、存放位置和后续访问方式。不能只相信客户端声明的媒体类型或扩展名。
若不可信输入进入头部，必须防止 CRLF 等控制字符破坏字段边界。参数化查询、正确的输出编码、严格解析与服务端权限校验各自解决不同问题。


05 · 浏览器侧安全头
响应头主要用途
Content-Security-PolicyCSP：限制脚本、资源、嵌入等行为，缓解 XSS 等风险，效果取决于具体策略。
Strict-Transport-SecurityHSTS：让浏览器在有效期内要求 HTTPS；首次访问的保障还涉及是否预加载等条件。
X-Frame-Options / CSP frame-ancestors限制页面被其他页面嵌入，降低点击劫持风险。
X-Content-Type-Options: nosniff限制特定场景下的 MIME 嗅探，必须与正确的 Content-Type 配合。
Referrer-Policy控制请求中发送多少来源地址信息，减少 URL 信息泄露。
这些头部是防护的一部分，不代替漏洞修复。CORS、CSRF 与 Cookie 属性的区别，见第 07、09 章。


06 · 从观察到证据的工作流
  1. 保存基线：记录原始请求、状态码、关键头、正文特征和耗时。
  2. 提出假设：例如“代理和应用是否采用了不同路径？”
  3. 只改一项：一次改变一个路径、方法、字段或参数。
  4. 比较并复现：区分稳定差异、缓存影响和偶发网络问题；记录工具会自动补充或修改的内容。
  5. 写出边界：说明触发条件、实际影响、可重复步骤和修复建议。
401 变 200、响应变长或变慢都只是线索，需要验证实际返回的数据和操作结果。curl 并非通用的原始字节回放器，浏览器、调试代理和命令行工具都可能规范化路径、解块或重算长度，边界研究时要核对实际发送的字节。
# Windows 示例：只在自己的本机靶场使用，按实际目标修改
curl.exe --http1.1 -i http://localhost:8080/
curl.exe --path-as-is -i http://localhost:8080/a/../b
curl.exe --resolve lab.example:443:127.0.0.1 https://lab.example/
--resolve 指定连接地址并保留 URL 中的主机语义；HTTPS 仍需要匹配、可信的证书。--path-as-is 限制 curl 自己移除部分路径点段，不会统一后端各组件的解析。


保留四个追问：
谁在解析？它相信谁？边界在哪里？能否稳定复现？安全实验请放在 CTF、自己的靶场或明确获得授权的环境。


本章一句话：把协议知识用来定位信任和解析问题，再用证据验证。

15 / KEEP THIS NEARBY速查

读请求
方法 → 目标 URL → 请求头 → 正文。
问：做什么、访问哪里、带了什么凭据、数据是什么格式？
读响应
状态码 → 响应头 → 正文。
问：成功了吗、返回什么类型、要跳转还是用缓存、是否更新 Cookie？
记住几个状态码
200 成功 / 201 创建 / 204 无正文
301、302 跳转 / 304 用已有缓存
401 认证凭据问题 / 403 拒绝 / 404 未找到
500 服务端错误 / 502 上游无效 / 504 上游超时
分清三组概念
Content-Type 描述正文；Accept 表达接收偏好。
Set-Cookie 让浏览器存；Cookie 随请求带回。
no-cache 可存但要验证；no-store 不存。
涉及身份时
认证是“你是谁”，授权是“你能做什么”。
HttpOnly 限制脚本读取，Secure 约束传输。
JWT 解码不等于验签，Base64 不等于加密。
涉及浏览器时
同源看协议、主机、端口。
片段 # 不直接随 URL 发给服务器。
跨源请求能否发送、响应能否读取，要分别判断。
